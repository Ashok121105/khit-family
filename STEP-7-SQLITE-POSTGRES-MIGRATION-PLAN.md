# STEP 7: Safe SQLite to PostgreSQL Migration Plan

## Scope and safety rules

This is a plan only. No data was migrated, no PostgreSQL table was created, changed, dropped, or overwritten, and no SQLite file or row was modified. Authentication, frontend files, and application behavior remain unchanged.

The inventory below was read from the live SQLite database at `database/khit_family.db` using read-only catalog queries and `COUNT(*)`. Counts are a snapshot and must be re-captured immediately before any future migration. No row values, passwords, connection strings, or other secrets are included.

### Constraints and indexes

- **Primary keys:** all 36 `id` columns are SQLite integer rowid primary keys. There are no composite primary keys.
- **Unique constraints:** `users.username`; `students.user_id`, `students.student_id`, `students.roll_number`; `faculty.user_id`, `faculty.faculty_id`; `departments.name`; `academic_years.name`; `buses.bus_number`; `fee_payments.transaction_id`; `app_settings.setting_key`; `(notification_id, student_id)` on both notification link tables; `(assignment_id, student_id)` on `assignment_submissions`; `(student_id, academic_year)` on `student_bus_assignments`; `(drive_id, student_id)` on `placement_applications`. SQLite auto-index names are implementation details and should become named PostgreSQL constraints.
- **Checks:** `profile_links` requires exactly one of `student_id` or `faculty_id` to be non-null in the declared schema; `fee_payments.amount > 0` is present in the base schema but must be rechecked against the live catalog/data before enforcing it in PostgreSQL.
- **Live named indexes:** `idx_students_department_year`, `idx_users_username_role`, `idx_students_user_id`, `idx_students_student_id_roll`, `idx_attendance_student_date`, `idx_attendance_student_subject`, `idx_marks_student`, `idx_marks_student_subject_date`, `idx_notifications_created_at`, `idx_notifications_audience_created_at`, `idx_notification_reads_student`, `idx_fees_student_year_status`, `idx_faculty_department`, `idx_assignments_subject_deadline`, `idx_assignment_submissions_student`, `idx_documents_student_visibility_created`, `idx_leave_student_status_created`, `idx_bus_assignments_student_year`, `idx_audit_logs_created_at`, and `idx_study_materials_target`.
- **Default values:** defaults are listed in the table inventory. Most timestamps use SQLite `CURRENT_TIMESTAMP`; numeric flags use `0`/`1`; status defaults include `Pending`, `Open`, `Applied`, `Private`, and `Draft` depending on table.

## 2. Feature ownership and relationships

- **Students and parents:** `students` is the student profile and account link. There is no `parents` table and no parent user account table. Parent name, mobile, email, and address are columns on `students`; parent access is therefore a lookup/use-case over student data, not a separate relational entity.
- **Users, admin, faculty, and authentication:** `users` stores username, bcrypt-compatible password hash, role, and creation time. `students.user_id` and `faculty.user_id` link role records to users. `password_reset_otps.user_id` links reset records to users. JWT creation/verification is application logic in `server.js`; it is not stored in SQLite.
- **Academic base:** `departments`, `academic_years`, and `subjects` support academic setup. The live `timetable` is a legacy denormalized table using department/subject/faculty text; the target schema proposes a normalized timetable with optional department, subject, and faculty IDs, so this requires an explicit mapping decision.
- **Fees:** `fees.student_id` is the parent for `fee_payments.student_id` and `fee_reimbursement.student_id`. The live fee payment table has no live `fee_id`, while the proposed PostgreSQL target does; do not invent fee links without a documented rule.
- **Attendance and exams:** `attendance.student_id`; `marks.student_id` and optional `marks.subject_id`; `result_records.student_id` plus user references for review/approval/publication/creation.
- **Notifications:** `notification_reads` and `notification_recipients` are many-to-many links from notifications to students. Both enforce one link per notification/student pair.
- **Content and files:** announcements, events, gallery, videos, study materials, assignments, assignment submissions, and documents. `documents` and several content tables hold URLs/paths or media references.
- **Transport:** `buses` -> `bus_stops`; `student_bus_assignments` links students to buses and optionally stops.
- **Leave:** `leave_requests` references students and optionally faculty reviewers; the live table retains both legacy (`from_date`, `to_date`, `response`) and canonical (`starts_on`, `ends_on`, `reviewer_remarks`) names.
- **Placements and internships:** `placement_drives` -> `placement_applications` -> students; internships are currently standalone.
- **Audit/settings/profile:** `audit_logs.user_id`, `app_settings.updated_by`, `achievements.student_id`, and `profile_links` to either student or faculty.

It is a starting point only and is not safe to run unchanged against the observed legacy shapes.

## 4. SQLite-specific changes required later

These changes are for a future PostgreSQL runtime/migration implementation. They are not being made in Step 7.

1. Replace synchronous `better-sqlite3` calls (`db.prepare().get/.all/.run`, `db.exec`) with an async `pg` pool/client abstraction. Convert `?` placeholders to PostgreSQL `$1`, `$2`, etc., and preserve parameter ordering.
2. Replace `result.lastInsertRowid` with `INSERT ... RETURNING id` (or an equivalent PostgreSQL result row). Do not assume SQLite rowid behavior.
3. Replace `INSERT OR IGNORE` with an explicit PostgreSQL conflict target and `ON CONFLICT (...) DO NOTHING`; use the correct unique constraint for each table.
4. Replace `sqlite_master` discovery and `PRAGMA table_info` with PostgreSQL catalog queries or remove runtime schema mutation from the application. Replace `PRAGMA foreign_keys`, `busy_timeout`, and `journal_mode = WAL` with PostgreSQL connection/transaction/pooling behavior.
5. Convert SQLite integer flags (`is_read`, `published`, `available`, `is_active`, `active`) from `0/1` to PostgreSQL `BOOLEAN`, with an explicit conversion rule and post-load checks.
6. Convert money/marks `REAL` to the target `NUMERIC` precision after checking scale and range; do not silently round. The target currently uses `NUMERIC(12,2)` for money and smaller numeric types for marks/grade values.
7. Convert `DATETIME` to `TIMESTAMPTZ` where the application means an instant; normalize date/time text first and document timezone assumptions. Keep date-only fields as `DATE` only when all values are valid dates.
8. Convert `metadata TEXT` JSON strings to `JSONB` only after validating every non-null value. Preserve invalid legacy text in an explicit fallback representation or quarantine it; do not discard it.
9. Preserve SQLite nullability during the first load. Several target columns are stricter than the live database, including `documents.title/category/file_path`, `assignments.subject_id`, `leave_requests.student_id/starts_on/ends_on/reason`, `events` content fields, and `departments.code`. Backfill and validate before adding `NOT NULL`.
10. Reconcile legacy/canonical columns before loading: `documents.document_name -> title`, `document_type -> category`, `file_url -> file_path`, `uploaded_at -> created_at`, `user_id -> uploaded_by`; `leave_requests.from_date/to_date/response -> starts_on/ends_on/reviewer_remarks`; `assignments.due_date/attachment_url/faculty_id -> deadline/attachment_path/assigned_by` only where the semantic mapping is approved; `buses.route_name/status -> route/available`; and corresponding legacy content columns.
11. The target schema currently contains columns absent from live data and live columns absent from the canonical target. Every table must use an explicit column list and transform; the current generic `SELECT *` migration loop must not be used without this reconciliation.
12. Preserve `NULL` versus empty string and check PostgreSQL comparison/case behavior for all search queries. PostgreSQL and SQLite differ in type coercion, boolean comparisons, date parsing, and some aggregate/type-affinity behavior.
13. Review startup seed routines before a cutover. In particular, `ensureResultSeedData()` can delete `result_records` when its seed condition is not met, and other startup routines insert demo rows. These must not run against a migrated production database unless deliberately redesigned.

## 6. ID, sequence, foreign-key, and index strategy

### IDs and sequences

Use PostgreSQL `BIGINT` identity columns or `BIGSERIAL`-compatible sequences in the new target schema. During the initial load, insert the original SQLite `id` values explicitly so all foreign keys continue to point to the same logical records. After each table load, set its sequence to at least `MAX(id)` using PostgreSQL sequence facilities. Validate that the next generated ID does not collide. Do not replace IDs with new values unless every dependent reference is remapped in one controlled transaction.

### Foreign keys

Create tables in dependency order and keep foreign-key checks enabled in PostgreSQL. Validate orphan counts before adding/enabling each constraint. Preserve the live delete actions where they are known: cascade for notification links, assignment submissions, student-owned records, buses/stops, placement applications, and password reset OTPs; set-null for reviewer/uploader references. Do not strengthen `NO ACTION` relationships or add target-only relationships until orphan and nullability checks pass.

### Indexes

Create named PostgreSQL equivalents of the live named indexes after bulk loading, unless query profiling justifies a revised index. Recreate all unique constraints as constraints, not only as indexes. Keep the target draft indexes for student/year, attendance, marks, results, notifications, fees, documents, audit logs, assignments, leave, buses, and study materials only after column names and data types are finalized. Run `ANALYZE` after loading and compare representative query plans.

## 7. Proposed migration order

1. Freeze a maintenance window and create a verified SQLite backup including `khit_family.db`, WAL/SHM files if present, and `uploads/`. Record the read-only row-count and checksum baseline.
2. Provision or select a dedicated empty PostgreSQL target. Do not run a schema script containing destructive statements and do not overwrite existing tables.
3. Reconcile the live schema against `postgres-schema.sql`; prepare an explicit versioned target schema with legacy compatibility columns and nullable staging fields where required.
4. Load independent reference tables: `users`, `departments`, `academic_years`, `subjects`, `buses`, `placement_drives`, `internships`, and other independent content tables after their column transforms are approved.
5. Load `students` and `faculty`, preserving user IDs and validating their user links. Resolve the embedded parent fields as student attributes; do not invent a parent table.
6. Load dependent academic/operational tables: `fees`, `attendance`, `marks`, `result_records`, `fee_reimbursement`, and `fee_payments` only after payment-to-fee mapping is resolved.
7. Load notifications and their link tables: `notifications`, then `notification_reads` and `notification_recipients`.
8. Load transport: `bus_stops`, then `student_bus_assignments`.
9. Load learning: `assignments`, `assignment_submissions`, and `study_materials`.
10. Load leave and placement applications: `leave_requests`, then `placement_applications`.
11. Load documents, announcements, events, gallery, videos, achievements, profile links, timetable, audit logs, app settings, and password reset OTPs after each target shape is validated. File records may be loaded only together with an independently verified upload-storage copy.
12. Recreate sequences, constraints, and indexes; run `ANALYZE`.
13. Run the validation checklist below, compare every table count, and perform read-only application smoke tests against a staging configuration.
14. Only after approval should a separate, explicitly reviewed cutover plan modify backend database routing. This Step 7 plan does not authorize that cutover.

## 8. Authentication and uploaded-file considerations

- Passwords are stored in `users.password` as hashes produced by `bcryptjs`; the migration must copy the hash strings byte-for-byte and must never export, print, reset, or rehash them as part of the data move. Verify password comparison in a staging environment without logging credentials.
- Preserve `users.id`, username uniqueness, role values, and `students.user_id`/`faculty.user_id` links. Do not migrate JWTs because they are not stored in SQLite; issue new tokens only after a later application cutover.
- `password_reset_otps` contains `otp_hash`, expiry, use time, and user link. Treat it as sensitive. A policy decision is required on whether expired/used rows are copied; if copied, validate hashes and timestamps without exposing them.
- Uploaded files are stored under the local `uploads/` directory. Database path/URL columns include `documents.file_url`/`file_path`, `study_materials.file_url`, `assignment_submissions.file_url`, `assignments.attachment_url`/`attachment_path`, and content media fields such as image/video/thumbnail URLs. The database migration alone does not move files. Copy and verify the upload directory separately, preserve relative `/uploads/...` references, and do not delete the source files until application reads are verified.
- `audit_logs.metadata` records upload metadata as JSON text and must be validated before conversion to JSONB. Never include its contents in logs or this plan.

## 9. Validation and rollback checklist

Before load:

- Re-run the catalog inventory and save counts, schema metadata, unique-constraint list, foreign-key list, index list, and a SQLite backup checksum.
- Check duplicate candidates, nulls in future `NOT NULL` columns, invalid dates, invalid numeric values, invalid boolean values, orphan foreign keys, malformed metadata JSON, and duplicate composite-key candidates.
- Confirm the target is the intended empty/dedicated database and that no destructive SQL is permitted.

During load:

- Use explicit source and destination column lists, staged transforms, parameterized inserts, and a transaction per controlled batch or table.
- Do not use the current generic `SELECT *` loop until the legacy column reconciliation is complete.
- Log table names, counts, and validation outcomes only. Do not log row values, password hashes, OTP hashes, file contents, or connection information.

After load:

- Compare row counts for all 36 tables, including zero-row tables.
- Compare primary-key ranges and sequence next values.
- Check every foreign-key relationship for zero orphans and every unique constraint for zero duplicates.
- Compare null counts and boolean distributions after conversion; compare monetary and marks sums with controlled numeric tolerance.
- Verify representative student, parent lookup, faculty, admin, fee, attendance, leave, result, notification, document, event, bus, assignment, placement, and settings reads.
- Verify bcrypt login checks in staging, password-reset behavior, JWT issuance, and role authorization without changing production authentication.
- Verify every stored upload path resolves to a copied file and that document deletion behavior is understood before cutover.
- Run backend tests, API smoke tests, and a read-only comparison of important dashboard aggregates.

Rollback/safety:

- Keep SQLite and its backup untouched and authoritative until all validation and a post-cutover observation window pass.
- If any validation fails, stop the cutover, discard only the isolated PostgreSQL staging target or roll back its transaction, and continue serving the unchanged SQLite application.
- Do not use `DROP TABLE`, `TRUNCATE`, `DELETE` against the SQLite source, or overwrite an existing PostgreSQL target as a rollback mechanism.
- Keep the upload backup and original upload directory until database and file references have been verified.

## 10. Files that will need modification later

No application code was changed for this plan. A future, separately approved migration/cutover will likely require:

- `database/postgres-schema.sql`: reconcile live legacy columns, nullability, constraints, data types, and indexes.
- `database/migrate-sqlite-to-postgres.js`: replace generic `SELECT *` loading with explicit table transforms, validation, sequence repair, safe conflict handling, and the approved migration order.
- `server.js`: replace SQLite query/API usage, remove SQLite-only startup schema mutation and seed behavior for PostgreSQL runtime, and preserve endpoint behavior.
- `create-admin.js`: replace SQLite access only after authentication cutover is approved; preserve bcrypt hash handling.
- `database/database.js`: replace the SQLite runtime connection only during the later cutover; do not remove `better-sqlite3` until rollback is no longer required.
- `database/backup-sqlite.js`: retain and possibly extend for final pre-cutover backup/checksum verification.
- `package.json`: only if the later runtime requires new scripts or dependency changes.
- `.env.example`/deployment configuration: only for documented, secret-free PostgreSQL runtime configuration; never commit actual credentials.

Frontend files are intentionally excluded from this Step 7 plan and were not changed.
